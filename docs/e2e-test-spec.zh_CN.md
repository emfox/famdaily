## 0. 这份文档是什么

`ui-spec.zh_CN.md` 是**设计草图**——它说"大概长这样"。这份是**验收合同**——它说"必须恰好这样，否则就是 bug"。

两者冲突时以本文为准。本文的每一条都是**可判定**的：要么过，要么不过，没有"看着还行"。

### 0.1 编号规则

| 前缀 | 范围 |
|---|---|
| `G-` | 全局规范（字体、触控、色彩、导航、无障碍） |
| `B-` | 启动与数据装载 |
| `H-` | 今日清单 |
| `C-` | 打卡动作（三态与弹层） |
| `N-` | 新建打卡项（三步） |
| `D-` | 项目详情与编辑 |
| `R-` | 历史与补卡 |
| `S-` | 统计 |
| `M-` | 成员 |
| `T-` | 设置与备份 |
| `E-` | 错误与边界 |

### 0.2 判定方式

| 代号 | 含义 |
|---|---|
| **【测】** | 已由 widget 测试自动断言（见各条 `test:` 标注） |
| **【眼】** | 需人工在真机核对（视觉/触感/系统行为） |
| **【双】** | 两者都要 |

一条测试写成"通过了"但没写【测】，视为未验证。

### 0.3 依据的规范

| 规范 | 用途 |

## 1. 全局规范（G）

### 1.1 字体：只用 M3 类型阶梯，禁止裸写 fontSize

**背景**：M3 的 15 级 type scale 是整套排版的地基。绕过它直接写 `fontSize: 10`，等于从阶梯上掉下来——系统字号放大时它不跟着放大，暗色模式下它的字重也不匹配。

| 编号 | 规格 | 判定 |
|---|---|---|
| **G-01** | `lib/` 下**不得出现**硬编码 `fontSize:`（`MemberAvatar` 内部按尺寸比例算的除外） | 【测】静态检查 |
| **G-02** | 所有文字必须取自 `Theme.of(context).textTheme.*` | 【测】静态检查 |
| **G-03** | 字号映射到 M3 阶梯后，最小不得低于 `labelSmall`（11sp），**正文不得低于 `bodySmall`（12sp）** | 【测】 |
| **G-04** | 页面标题用 `headlineSmall`（24sp）；AppBar 内标题用 `titleLarge`（22sp）；分节标题用 `titleMedium`（16sp） | 【测】 |
| **G-05** | 列表主文案 `bodyLarge`（16sp）/ `titleSmall`（14sp）；元信息 `bodySmall`（12sp）；标签 `labelMedium`（12sp） | 【测】 |
| **G-06** | 用户调大系统字号（1.3×）后，**不得出现文字被裁切**（`TextOverflow.clip` + 固定高度） | 【眼】设置 → 显示 → 字体大小 |

**M3 type scale 参考值**（用于核对 G-03~G-05）：

| Token | 字号 / 行高 | 字重 | 本项目用途 |
|---|---|---|---|
| `headlineSmall` | 24 / 32 | 400 | 页面标题（今日/历史/设置/统计） |
| `titleLarge` | 22 / 28 | 400 | 弹层标题、AppBar 标题 |
| `titleMedium` | 16 / 24 | 500 | 分节标题、成员名、进度数字 |
| `titleSmall` | 14 / 20 | 500 | 打卡项名称 |
| `bodyLarge` | 16 / 24 | 400 | 表单输入、长句正文 |
| `bodyMedium` | 14 / 20 | 400 | 次要正文、按钮下方说明 |
| `bodySmall` | 12 / 16 | 400 | 元信息（时间、"迟 N 分钟"） |
| `labelLarge` | 14 / 20 | 500 | 按钮文字、分组标题 |
| `labelMedium` | 12 / 16 | 500 | 角标、步数 |
| `labelSmall` | 11 / 16 | 500 | 最小标签（"预览"） |

### 1.2 触控目标

| 编号 | 规格 | 判定 |
|---|---|---|
| **G-07** | 所有可点元素的可点区域 ≥ **48×48dp**；视觉图标可小于 48，但 `SizedBox`/`InkResponse` 必须撑到 48 | 【测】检查 `_StatusMark` 等 |
| **G-08** | 相邻可点元素的**可点区域**之间空隙 ≥ 8dp | 【眼】 |
| **G-09** | 顶栏按钮（返回/关闭/更多/保存）的可点区域 ≥ 48×48dp | 【测】 |

### 1.3 色彩与对比度

| 编号 | 规格 | 判定 |
|---|---|---|
| **G-10** | 正文文字与其背景对比度 ≥ **4.5:1**；≥18sp 的大字或 ≥14sp 粗体 ≥ **3:1** | 【测】用 luminance 计算逐对核验 |
| **G-11** | 状态**不能只靠颜色**区分：五态各自都要有独立的形状/文字（实心圆 / 空心圆+勾 / 叉 / 空心圈 + 副标题文字） | 【测】 |
| **G-12** | 全部色彩取自 `ColorScheme`，不得出现 `Color(0xFF...)` 字面量（种子色定义处除外） | 【测】静态检查 |
| **G-13** | 暗色模式（`ThemeMode.system` + 系统深色）下所有页面可读，无白底白字 | 【眼】 |

### 1.4 导航骨架

| 编号 | 规格 |
|---|---|
| **G-14** | 一级页 3 个：**今日 / 历史 / 设置**，底部 `NavigationBar`，三个 `NavigationDestination`，当前项图标为实心变体 |
| **G-15** | 切 Tab 不重建页面（`IndexedStack`），滚动位置保留 |
| **G-16** | 二级页从右侧滑入，AppBar 左侧为返回；**没有**底部 Tab |
| **G-17** | 系统返回键 / 返回手势 = 页面内返回，行为一致 |
| **G-18** | 二级页 AppBar 标题左对齐，不居中对齐（Android 规范），`titleSpacing` 与一级页一致 |
| **G-19** | 模态弹层从底部升起，背景变暗（scrim），点 scrim 或下拉可关闭 |
| **G-20** | 窗口宽 ≥ 600dp（Medium 及以上）时，内容最大宽度 **840dp 居中**，不得拉伸成整行文字 |【眼】 |

### 1.5 响应与反馈

| 编号 | 规格 |
|---|---|
| **G-21** | 任何写操作完成到界面更新 ≤ 1 帧（不留"旧状态"让人重复点） |
| **G-22** | 防重入：同一操作在飞行中时按钮不可点，且**按钮文字不变**（不拿文字当提示牌） |
| **G-23** | 写操作失败必须**给出口**：显示错误（SnackBar）且页面可退出，不得把用户锁住 |
| **G-24** | SnackBar 只显示一条（先 `hideCurrentSnackBar`），停留 4 秒，不出现在底部导航下方被遮挡 |

## 4. 打卡动作（C）

### 4.1 四种点击路径

| 编号 | 前置状态 | 操作 | 期望 |
|---|---|---|---|
| **C-01** | 待做（未到点） | 点状态标记 | **立即**变实心绿 + 标题加删除线 + 副标题变「HH:mm · 准时」+ 进度 +1；随后**自动弹出**「记一句」弹层（C-10） |
| **C-02** | 已过时间 | 点状态标记 | **不直接打卡**，弹出「两个出口」弹层（C-05） |
| **C-03** | 准时 / 补卡 / 没做 | 点状态标记 | 直接撤销，回到待做；不弹任何确认 |
| **C-04** | 任意状态 | 点文字区 | 进入项目详情（D-01） |

> **C-02 的理由**：已经过点，系统无法判断"刚做"还是"漏了"。直接记成准时是在帮用户撒谎。

### 4.2 漏卡两个出口弹层

| 编号 | 规格 |
|---|---|
| **C-05** | `showModalBottomSheet`，带拖拽把手，内容左右内边距 20dp、底部 20dp |
| **C-06** | 标题：任务名 `titleLarge`；下方 4dp 处 `bodyMedium` 灰色「HH:mm · 这件事最后怎么样？」 |
| **C-07** | 两张选项卡，圆角 14dp，内边距 16/14，图标 + 12dp + 两行文字（`titleSmall` 标题 / `bodySmall` 灰色副标题）：<br>① `check_circle_outline`「做了，只是当时忘了记」/「记为补卡 · 算完成不算准时」，`primaryContainer` 50% 底、`primary` 图标<br>② `close`「没做」/「老实记一笔，这条就结案」，`errorContainer` 35% 底、`error` 图标 |
| **C-08** | 底部 `TextButton`「算了，不改」→ 关闭弹层，**不改任何数据** |
| **C-09** | 点 ① → 记为补卡（空心绿勾），副标题「HH:mm · 补卡」；点 ② → 记为没做（灰叉），副标题「HH:mm · 没做」；两者都**不弹**「记一句」 |

### 4.3 「记一句」弹层

| 编号 | 规格 |
|---|---|
| **C-10** | 弹层左右 20dp，底部 `viewInsets.bottom + 20`（键盘弹出时整体上移，输入框不被遮） |
| **C-11** | 标题「任务名 · 记一句」`titleMedium` |
| **C-12** | 12dp 后 `TextField`：`autofocus: true`，1–3 行，`OutlineInputBorder`，hint「比如：今天吃了两粒，有点反胃」 |
| **C-13** | 12dp 后两个 `OutlinedButton.icon`：「拍一张」(`photo_camera_outlined` 18dp)、「从相册选」(`photo_library_outlined` 18dp)，间距 8dp |
| **C-14** | 选好照片后：显示 120dp 高预览（圆角 10dp，`BoxFit.cover`），右上角 6/6 处一个 24dp 圆形删除按钮 |
| **C-15** | 拍照/相册失败：预览区下方 8dp 显示 `bodySmall` error 色「打不开相机或相册（…）。可以先把照片存到相册里再选。」 |
| **C-16** | 底部右对齐：`TextButton`「不用了」+ 8dp + `FilledButton`「保存」 |
| **C-17** | 点「不用了」或点 scrim 或下拉 → 关闭，**打卡结果保留**，不写备注 |
| **C-18** | 点「保存」→ 关闭并落库；备注为空且无照片时等同于 C-17 |
| **C-19** | 键盘上回车（`TextInputAction.done`）等同点「保存」 |
| **C-20** | 照片落盘失败：不留半条脏数据，SnackBar「照片没存上（可能太大了），备注已经记下」 |

### 4.4 撤销与时限

| 编号 | 规格 |
|---|---|
| **C-21** | 撤销 = 删除该条记录，回到待做态 |
| **C-22** | 超过 **30 天**的记录不可撤销：点状态标记时 SnackBar「超过 30 天，不能再改了」，状态**不变** |
| **C-23** | 打卡后立即取消该槽位的待发提醒（不等下次全量重排） |

## 5. 新建打卡项（N）

### 5.1 总则

| 编号 | 规格 |

### 15.0 第二轮：软删除成员在历史里的显示（用户报障）

用户原话：**「历史的统计项里面，人名显示的都是已删除的成员。」**
先写复现测试，结果是 `StatsService` 本身没错（删掉一个人后 `rows` 只剩另一个）。
真正的原因在别处——**同一个问题有两个面**：

| 条目 | 原状 | 问题 | 处理 | 状态 |
|---|---|---|---|---|
| **R-19 / D-03a** | 明细页与详情页都写死 `member?.name ?? '已删除的成员'`，而成员表来自 `listMembers()`（过滤了已删除） | 所有被删的人**撞成同一句话**，「那天是谁做的」这条信息没了；两个人被删就等于两行一模一样 | 新增 `listMembersIncludingDeleted()`；名字照留，后面挂「已删除」；已删的不画头像；兜底文案改「不认识的成员」 | ✅ |
| **R-18** | 分组按"有槽位"分，包括一堆一个字的没记的 | 删掉成员后，她过去**每一天**都还在日历里占一个分组，整组只有一句「已删除的成员」——用户翻到哪天都觉得"统计里全是已删除的" | 分组只给**有 `record`** 的行；没记的统一归到末尾「没记录」组，不挂人名 | ✅ |
| **R-21** | 整天没记时照样画一堆行 | 一堆没人名的行撑版面，比空状态更像出错 | 全无记录时走空状态「这天没有打卡记录」 | ✅ |
| **D-03a** | `TaskDetailService` 里 `isDeleted ? null : member` | 数据层就把名字扔了，界面再想显示也没救 | 改为 `member: member`，头像画不画交给界面 | ✅ |

这里值得记一条：**用户描述的现象（"统计项里"）和他实际看到的地方（历史明细）往往是两回事**。
报告里那句"统计项"指的其实是明细页的分组标题。照着他的字面去找 `StatsService`，
会得出"代码是对的，用户看错了"这种结论——而那是在把 bug 说成误解。

### 15.0b 第三轮：刚建的成员，历史里也显示成"已删除"

用户原话：**「我的成员是刚新建的，没有删除，然后马上建一条打卡并打卡，然后切到历史 tab，查看当天，显示是一个已删除成员。」**

先按他的话复现了一遍数据层：新建成员 → 建项目 → 落槽位 → 打卡 → `loadDay`。
结果完全正常（`members: [m-new/小明/false]`，那一行 `memberId=m-new`）。
`StatsService`、`listMembersIncludingDeleted()`、软删除写入也都逐个查过，没有一处会把没删的人标成已删。

不动数据层，改从**真实入口**复现：`HistoryPage` → 点月历某天 → 明细页。一测就出来了。

| 条目 | 原状 | 问题 | 处理 | 状态 |
|---|---|---|---|---|
| **R-22** | `HistoryPage._openDay` 构造 `DayDetailPage` 时**没传 `db`**，而 `DayDetailPage.db` 是可空的（"null 表示只读浏览"） | 页面不崩、不报错，但读不到成员表，**每一组标题都退化成「不认识的成员」**。用户看到"人的名字都不对"，自然会理解成"人被当成删掉了" | `HistoryService` 暴露 `db` getter；历史页显式传 `widget.service.db` | ✅ |

这条的真正教训是**测试的入口错了**：`day_detail_page_test.dart` 一直是自己
`pump(DayDetailPage(db: db))`，把库硬塞进去。于是"历史页忘了传库"这件事
在 500 多个用例全绿的情况下真实存在了好几个版本。补的 `test/feature/history_page_test.dart`
只做一件事：**从 `HistoryPage` 点进去**，断言看得见真名。
把修复撤掉跑一遍，这个文件立刻红 2 条——说明它真的守得住。

顺带记一句：这类"可空依赖 + 网页自己兜底"的组合很危险。兜底文案让页面看起来正常，
`AppDatabase?` 让漏传在编译期合法，两件事一起就把 bug 藏住了。
要么把依赖改成 `required`，要么至少留一条从真实入口进去的测试。

#### 测试脚手架上的四个坑（都不是 App 的问题，但都很费时间）

这一节留给下一个人，省得重踩：

1. **`withClock` 在集成测试里失效**。
   `package:clock` 是把 Clock 塞进 `Zone.current` 的 zoneValue。单元测试都在同一个 zone，好用；
   但 `IntegrationTestWidgetsFlutterBinding` 是 live binding，页面的 `initState`/`build`
   跑在**引擎那侧的另一个 zone**。实测打印：
   ```
   BODY  zone=18070123 clock=2026-03-02 20:00   ← 测试体
   BUILD zone=159873591 clock=2026-10-24 00:39  ← 页面
   ```
   症状极迷惑：测试体里 `clock.now()` 明明是 3 月，日历画出来是 10 月。
   解法是 `lib/app/test_clock.dart`：把"现在几点"放进一个**全局变量**，
   页面统一走 `appNow()`，任何 zone 读到都一样。生产构建里 `TestClock.enabled`
   永远是 false，走的就是普通 `clock.now()`。

2. **打卡后的底部面板会吃掉后面所有点击**。
   打卡成功会 `showModalBottomSheet` 出「记一句 / 加张照片」，带一层 ModalBarrier。
   不收掉它，后面点底部导航"成功"但什么都没发生——症状是"切不到历史页"。
   另外判断关没关**不能数 `ModalBarrier`**：Navigator 常驻一层，从 2 变 1 才是真关了。
   判据要用「`BottomSheet` 还在不在」。

3. **`find.text('历史').last` 会点错地方**。
   首页打卡详情里也有一行「历史」字样。`.last` 点到它上面，tab 不会切，
   测试继续往下跑，然后在一个完全无关的地方报错。必须在 `NavigationBar` 里找。
   同理，`popToRoot` 的判据也不能用 `find.text('今日')`——它会被假阳性满足。

4. **多点一次不如断言到达**。
   真机渲染下偶尔第一次点只上了水波纹。`goToTab` 现在的做法是：点 → 断言目标页
   在树上 → 没到就重点，三次还不到就 `fail`，而不是带着错误状态往下跑。

### 15.0d 第五轮：统计的「本月」是空的（用户报障）

用户原话：**「历史tab的右上角 统计 页面，本月是空的」**。

#### 根因不在统计，在重排

统计的分母来自 `slots` 表——统计本身没有任何"取数范围"的问题，它老老实实
读 `[月初, 今天]` 这个区间。问题是**库里没有这些行**。

`ReminderScheduler.reschedule` 里展开的起点是 `today`：

```dart
Scheduler.expand(specs: specs, from: today, to: windowEnd)
```

这是"给通知排班"的思路——过去的班次没必要排。但 `slots` 表被复用成了
**统计和历史的分母**，于是排班逻辑的历史盲区直接变成了统计的空洞：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 每天都会打开 App | 每天的槽位都排上了，正常 | 正常 |
| 隔了 19 天再打开 | 本月只有今天 1 条 →「本月」几乎空白 | 1 号到今天全在 |
| 月中才建的项目 | 只从创建日起 | 只从创建日起（**设计如此**） |

最后一行值得说清楚：往月补齐的起点是 `max(月初, 规则生效日)`，而生效日就是创建日。
月中建的项目不会凭空补出上半月的槽位——那时候这个项目还不存在，补出来是造数据。

#### 修复的分寸：补历史绝不能顺手删历史

原来的落库只有一条路：

```dart
_replaceSlots(expansion.slots, from: today, to: windowEnd)  // 先 delete 再 insert
```

`replaceSlots` 会先删掉窗口内的所有槽位再重灌——这对"规则改了要作废旧排班"是对的。
但如果把历史段也交给它，删的是 `[from, to]`，窗口起点一动就可能抹掉有用的东西。

所以新增 `backfillSlots`：**只 insert，没有 delete**。两段分开写：

| 段 | 区间 | 写入口 | 会不会删 |
|---|---|---|---|
| 历史 | `[月初, 昨天]` | `backfillSlots` | 不会 |
| 未来 | `[今天, 窗口末]` | `replaceSlots` | 会（窗口内整段重灌） |

另外，`expand` 的 `maxSlots` 上限是按槽位数给的常量。往前多展开 30 天，
如果上限不跟着放宽，历史槽位会**把未来的挤掉**——修了统计，废了提醒。
现在上限是 `policy.maxScheduled + today.daysSince(historyStart) * daily`。

#### 通知只给未来的

往回展开出来的槽位只当分母，不进规划器：

```dart
final upcoming = [for (final s in expansion.slots) if (!s.date.isBefore(today)) s];
NotificationPlanner.plan(expanded: upcoming, ...)
```

否则用户会在 20 号晚上收到「3 月 3 日的降压药还没吃」。这条单独写了一条用例守着。

|---|---|

| `app/test/feature/stats_service_test.dart` | group「本月不该是空的」2 条，从统计出口断言 |

反向验证：撤掉往月展开，4 条立刻红。修复前后用探针看过同一个场景
（3 月 20 日启动）：`expected` 从 `1` 变成 `20`，而 `planned` 保持 `26` 不变——
分母补上了，通知没多发。

#### 这一轮的方法论收获

前一轮刚建好端到端测试，这一轮的问题**它也没抓住**——因为 5 条端到端都是在
"同一天里"跑完的，压根没跨天。这说明：

> 端到端不等于"用真 App 跑一遍"，**时间维度得单独设计**。
> 业务里凡是"按天累积"的东西（分母、连续天数、趋势），都要有一条
> "隔了很久再打开"的用例。

这一轮的 6 条用例实际上是补上这个缺口的，虽然它们落在单元层（`ReminderScheduler`
和 `StatsService` 都是纯逻辑，假时钟一钉就能精确构造 30 天的跨度，比端到端更划算）。

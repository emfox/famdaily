# 成员链接管理（作废链接）

## 1. 为什么要有这份文档

`POST /members/:id/link` 生成链接、`POST /members/:id/unlink` 作废链接，两条接口和 `SyncService` 的封装早已存在，但**作废这条链路没有任何界面调用**——`revokeMemberLink` 至今是一个零调用方的公开方法。

而这个功能的边界一旦认真想，会连带出三个必须拍板的问题：

1. 用户**无法知道**"这个成员现在有没有有效链接"（服务端只存哈希）
2. 服务端在"本来就没链接"时返回 `revoked: false` 且**不报错**，界面该说什么
3. 作废**不可逆**，误触的代价是"老人的打卡入口突然打不开了，而他不会告诉你"

单机版的经验是：**先写清界面上每一句话和每一个状态，再动手。**

## 2. 它解决什么

爷爷的打卡链接被转到了家族群里。持有人需要**立刻关掉它**，而不是"重新生成一个"——重新生成只是产生新链接，旧链接会因哈希被顶掉而失效，但**用户无法确认这一点**，也得不到任何反馈。

```
App（持有人）                              服务端
   │                                          │
   │ 点「作废这个链接」                        │
   │ 二次确认「作废…？」                       │
   │ 确认                                      │
   │ POST /members/:id/unlink ──────────────► │
   │                                          │ 清 members.web_token_hash
   │                                          │ 清 web_token_issued_at_ms
   │                                          │ DELETE web_tickets（该成员全部）
   │ ◄──── { ok, memberId, revoked, clock } ── │
   │                                          │
   │ revoked=true  → 「已经作废，旧链接打不开了」
   │ revoked=false → 「本来就没有有效链接」
```

> **关键点**：服务端同时删掉该成员所有已签发的 ticket（Cookie）。
> 作废不只是"以后不能用"，而是"现在正在用的那台手机也会立刻被踢出来"。
> 用户以为的影响面比实际的小，是最常见的误判 —— 所以它必须写进确认弹窗。

## 3. 三个关键决策

| 决策 | 选择 | 否决的选项与原因 |
|---|---|---|
| 入口位置 | **链接弹窗 ready 态里的次要按钮** | ① 详情页独立一行：没链接时点进去只会得到 `revoked:false`，白跑一趟；② 两处都放：同一件事两个入口，文案要维护两份，且详情页那个在"没生成过链接"的常见情况下是死的 |
| 作废后 | **弹窗当场变终态，只留「知道了」** | 加「重新生成一个」：等于把"重新生成会让旧的失效"这句说明绕回去了；而且用户刚意识到"链接泄露了"，该做的是**先止血**，不是马上再造一条可能再次泄露的 |
| `revoked` 语义 | **两层都改签名透传到界面，分两句不同的话** | 统一说"已作废"：一个从没生成过链接的成员也会看到这句话，那是**假的**。这和本文档 §9 的"已知限制"一样，宁可说"没有"，不说"已经" |

## 4. 界面状态机

`MemberLinkSheet` 从 4 个状态扩到 8 个。

> **不用 `bool` 字段区分两个终态**：`switch` 少一个分支时 `bool` 不会报错，枚举会。
> 这也是把 content/actions 从 `_Phase.error || _Phase.unpaired` 这种**或模式**改成
> **逐值穷举**的原因——或模式在新加枚举值时不触发穷举检查，等于白拿一层保护。

```
                    ┌─────────┐
        打开弹窗 ──► │ loading │
                    └────┬────┘
              ┌──────────┼──────────┬───────────┐
              ▼          ▼          ▼           ▼
          ┌───────┐  ┌───────┐  ┌───────┐  ┌──────────┐
          │ ready │  │ error │  │unpaired│ │（同上）  │
          └───┬───┘  └───────┘  └───────┘  └──────────┘
              │            ▲          │
   点「作废」 │            │再试一次  │知道了（关）
              ▼            │          ▼
     ┌────────────────┐    │        （退出）
     │ 二次确认（嵌套）│    │
     └───┬────────┬───┘    │
    再想想│        │确认    │
         ▼        ▼        │
      （回 ready）┌─────────┐│
                  │revoking ││
                  └────┬────┘│
          ┌────────────┼─────┴──────┐
          ▼            ▼            ▼
    ┌──────────┐ ┌──────────────┐ ┌──────────────┐
    │ revoked  │ │revokedNothing│ │ revokeFailed │
    └──────────┘ └──────────────┘ └──────┬───────┘
                                         │再试一次
                                         └──► revoking
```

### 4.1 各状态的文案与按钮（逐字，实现时照抄）

| 状态 | 内容 | 按钮（左→右） |
|---|---|---|
| `loading` | ⏳「正在生成…」 | 「取消」 |
| `ready` | 说明句 + URL 框 + 两行小字（见下） | **「作废这个链接」**、复制、**分享** |
| 二次确认（嵌套） | 标题「作废{名字}的打卡链接？」，正文三行（见 4.2） | 「再想想」、「作废」 |
| `revoking` | ⏳「正在作废…」 | **无按钮**（请求已发出，不能取消） |
| `revoked` | 「{名字}的打卡链接已经作废，旧链接打不开了。\n他要用，得找你要一个新链接。」 | 「知道了」（Filled） |
| `revokedNothing` | 「{名字}现在没有有效的打卡链接，不用作废。\n他要打卡的话，找你要一个新链接就行。」 | 「知道了」（Filled） |
| `revokeFailed` | 失败原因 + 「确认之前，这条链接还是可以发的：」+ URL 框 | 复制、「知道了」、「再试一次」 |
| `error` | 「生成失败了：…」 | 「知道了」、「再试一次」 |
| `unpaired` | 具体原因（见 §6） | 「知道了」 |

**`ready` 态的两行小字**（原有一行 + 新增一行）：

```
这个链接只显示这一次，关掉就再也看不到了。重新生成会让旧的失效。
链接发给过别人（或者转发到群里）的话，可以用下面的「作废这个链接」马上关掉它。
```

第二行是必须的：没有它，用户不知道那个按钮是干什么的，也不知道"我已经把链接发出去了"是不是还有救。

### 4.2 二次确认弹窗（逐字）

- **标题**：`作废{名字}的打卡链接？`
- **正文**：
  ```
  作废之后，这条链接就永远打不开了，没法恢复。
  已经打开过这条链接的手机，会马上退出登录。
  已经打过的卡都在，一条不少。
  ```
- **按钮**：「再想想」→ false，「作废」→ true
- **`barrierDismissible: false`**

三条正文各自的理由：

| 行 | 为什么必须说 |
|---|---|
| 「永远打不开了，没法恢复」 | 不可逆必须明说。别的破坏性操作（删成员、删项目）都写了"记录还在"，这里同理要写"什么会没" |
| 「已经打开过这条链接的手机，会马上退出登录」 | **影响面比用户想的大**。用户以为"以后不能用"，实际是"现在正在用的也会被踢"——爷爷正在打卡时被踢出去，他会以为手机坏了 |
| 「已经打过的卡都在」 | 用户最怕的是"作废链接把打卡记录也删了"。事实是不删，必须说 |

**「作废」按钮不带危险色**：项目里 4 处确认弹窗的肯定按钮都是普通 `TextButton`
（只有同步页的「断开」用 `FilledButton`），危险色只用在**入口**上。
这里的入口是 `ready` 态那个「作废这个链接」，它带 `foregroundColor: error`。

## 5. 状态转换的行为断言

每条都可测。编号 `L-xx`，与 [e2e-test-spec §7.3](./e2e-test-spec.zh_CN.md) 的 `M-xx` 段对应。

| 编号 | 断言 |
|---|---|
| **L-01** | 点「作废这个链接」**只弹确认框，不发请求**（`calls` 里仍然只有 `/link`） |
| **L-02** | 确认框点「再想想」→ 回到 `ready`，URL 还在，复制/分享仍可用，**`/unlink` 一次都没发** |
| **L-03** | 确认后立刻进 `revoking`，**没有任何按钮**（不能取消已发出的请求） |
| **L-04** | `revoked: true` → `revoked` 态，**不再显示 URL**（哈希已清，留着会让人以为还能用），没有「分享」「再试一次」「重新生成一个」 |
| **L-05** | `revoked: false` → `revokedNothing` 态，文案**不含「已经作废」**四个字 |
| **L-06** | 响应体缺 `revoked` 或不是 bool → 等同 `revokedNothing`，**不进 `revokeFailed`**（副作用已发生，不能说"失败"） |
| **L-07** | 401/403 → `revokeFailed`，文案含「凭据失效」「没做成」，**不给「再试一次」** |
| **L-08** | 连不上 / 超时 → `revokeFailed`，文案含「可能还没作废」，**给「再试一次」**，URL 仍可见可复制 |
| **L-09** | **404 → 当作 `revokedNothing`，不说失败**：成员在服务端已不存在，他的链接自然也不可能再用 |
| **L-10** | 失败后点「再试一次」成功 → 进 `revoked`（`/unlink` 被调用两次） |
| **L-11** | 三个终态都不出现「重新生成一个」 |
| **L-12** | 终态按返回键只关弹窗，**不连带关掉成员详情页** |
| **L-13** | 弹窗的「作废这个链接」入口**只在弹窗里**，成员详情页列表里没有 |

### 5.1 两个终态为什么必须是两句不同的话

`revoked: false` 的含义是"服务端本来就没有有效链接"。这种情况下说"已作废"会造成两个具体后果：

1. 用户以为"刚才有人废过一次"，开始怀疑家里其他人
2. 用户以为"我确实关掉了那个泄露的链接"，而实际泄露的那条可能属于**另一个成员**——他会就此收手

所以 `revokedNothing` 说的是**状态**（现在没有有效链接），不是**动作**（我刚作废了）。

### 5.2 「可能还没作废」为什么必须带"可能"

超时和连不上**无法区分**"请求没到服务端"和"服务端处理完了但响应没回来"。两种确定的说法都是撒谎：

- 说"没作废" → 服务端其实已经清了，用户又去重新生成，等于白折腾
- 说"已作废" → 服务端其实没收到，用户以为安全了，泄露的链接还能用

这是本功能**唯一**必须用不确定语气的句子。

## 6. 失败分支的完整对照

| 异常 | 界面话术 | 「再试一次」 | 链接还有效吗 |
|---|---|---|---|
| `SyncNotPairedException` | 还没有同步过，没法作废。先去「设置 → 同步」配对吧。 | ✗ | **还有效**（请求没发出去） |
| `SyncAuthException` 401/403 | 这台设备的同步凭据失效了（{code}），作废没做成。去「设置 → 同步」重新配对之后再来。 | ✗ | **还有效**（鉴权层就拒了） |
| `TransportException` | 连不上服务：{msg}。链接**可能**还没作废。 | ✓ | **不确定** |
| `SyncHttpException` 404 | （不进失败）→ `revokedNothing` | ✗ | **已无效** |
| `SyncHttpException` 其它（500/503/429） | 服务端说：{msg}。链接**可能**还没作废。 | ✓ | **不确定** |
| 其它 | 作废失败了：{e}。链接**可能**还没作废。 | ✓ | 不确定 |

两条铁律：

1. **失败后绝不显示"已作废"**，也绝不自动重试。
2. **失败后 URL 必须仍然可见可复制** —— 请求可能根本没到服务端，用户还需要这条链接。

## 7. 数据层怎么改

### 7.1 `SyncApi.revokeMemberLink` → `Future<bool>`

```dart
final resp = await _transport.post(/* 不变 */);
_throwOnError(resp, '/members/unlink');
final revoked = resp.json?['revoked'];
return revoked is bool ? revoked : false;   // 缺失/类型不对 → 保守的 false
```

- **字段异常不抛错**：副作用（链接真的被清了）在收到响应时已经发生。抛错会让界面走进"失败了，再试一次"，用户点第二次只会得到 `revoked:false` 和"本来就没有链接"——比诚实地说"可能没废掉"更误导。
- 这与同文件 `memberLink` 的严格风格**故意不一致**：`memberLink` 拿不到 `url` 就没法用，必须报错；`unlink` 的返回值只影响措辞。

### 7.2 `SyncService.revokeMemberLink` → `Future<bool>`

只改返回类型 + 把 `await` 改成 `return await`，`finally { api.close(); }` 不变。

### 7.3 顺手修 `_throwOnError` 的 message 解析（**必须先修**）

原实现只认**字符串**形状：

```dart
final detail = resp.json?['error'] ?? resp.json?['message'];
final text = detail is String ? detail : 'HTTP $code';
```

而服务端的真实形状是 `{ error: { code, message } }`（`server/src/http.mjs` 的统一出口）。
于是所有服务端错误在 App 上退化成 `HTTP 404` 这种话。

> ⚠️ 这个缺陷一直没被测试发现，因为**现有 5 处测试喂的全是字符串形状**。
> 测试和实现一起"只认字符串"，等于给这个 bug 盖了个章。

修法：两种形状都认 —— 字符串（早期测试、网关 502）优先，对象取 `message`，
再退到顶层 `message`，最后才是 `HTTP {code}`。

为什么这次必须修：本功能里 404「没有这个成员」是**唯一**能给出有意义提示的 HTTP 错误，
`HTTP 404` 对老人完全无效。

## 8. 交互细节的刻意选择

| 现象 | 原因 |
|---|---|
| 确认框 `barrierDismissible: false` | ① 破坏性操作，点外面就"什么也不做"，这个"安全"是假的；② 更糟的是**点遮罩会关掉下面那层**——老人连点两下很常见，第二下落在链接弹窗遮罩上，屏幕上的 URL 就再也拿不回来了 |
| 链接弹窗本身也改 `barrierDismissible: false` | 作废入口出现后，误触遮罩的代价第一次变大：想"先复制再去作废"却先把 URL 弄丢了，只能重新生成，而**重新生成等于把本来不想废的那条也废了** |
| `revoking` 态一个按钮都不给 | 请求已经发出去了。「取消」在这里只是"关掉界面"，会让人以为作废被撤销了 |
| 终态清空 `_url` | 哈希已清，把 URL 留在屏幕上等于暗示它还能用 |
| 不作废时也**不提示**该作废 | 这个功能不做"链接已发出 30 天"之类的提醒。App 拿不到链接状态，任何提示都是猜的 |
| 不做「重新生成一个」 | 见 §3 |
| 入口按钮带 `error` 色、确认按钮不带 | 项目既有模式：危险色只在入口 widget 上 |

## 9. 已知限制

- **App 无法知道"当前有没有有效链接"**。服务端只存哈希，`members` 表也没有这个标记。所以入口不能写「作废链接（当前有效）」，只能写「作废这个链接」，靠 `revoked` 的返回值在事后说明。要做"提前显示有没有"，得加接口或字段——本轮不做。
- **作废是全局的，不分设备**。任何一台配对设备作废，这个成员在所有设备上的链接和 Cookie 一起失效。这是服务端 `(family_id, member_id)` 作用域决定的，符合需求（"持有人可随时作废某个成员的所有链接"）。
- **没有"作废历史"**。作废后想追溯"谁在什么时候废的"没有记录。多人共用同一个家庭账本时这可能是个问题，但目前没有需求。
- **网页端在作废后不会主动得知**。它要等下一次 `/m/api/today` 返回 401 才会说"让家里人重发链接"（见 [web-member-page §5](./web-member-page.zh_CN.md)）。页面正好开着的话，用户会看到一次失败提示，而不是"立刻被踢"。

## 12. 反向验证（防"假绿"）

这个功能最容易假绿的地方是**用 `revoked: true` 的用例去测"透传"**——把实现改成恒返回 `true`，那条用例照样绿。所以每条探测值都必须能穿过被破坏的那条路径。

| # | 破坏 | 期望变红的断言 | 为什么要这样设计探测值 |
|---|---|---|---|
| 1 | `revoked is bool ? revoked : false` → `true` | L-05：`revoked:false` 时出现「已经作废」 | 探测值必须是 `revoked: false`。用 `true` 的用例测不出"透传" |

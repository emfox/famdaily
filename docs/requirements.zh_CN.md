## 1. 一句话定位

一款**以家庭为单位**的打卡工具：一个账号里维护一份家庭成员列表，给每个人设定每天要做的固定事项（吃药、跳绳、喝水……），按时提醒、一键代打卡、看完成情况。

**和市面上"习惯打卡 App"的差别**：核心不是"培养个人习惯"，而是**多人关怀**——尤其是老人吃药、小孩作息这类"我不在你身边也想确认你有没有做"的场景。

---

## 2. 账号与角色（已定：极简单账号）

**只有一个概念：登录账号（你）。** 没有"档案"、没有"家庭组"、没有邀请绑定、没有权限体系。

```
账号（你）
  └── 成员列表（通讯录式的人名）
        ├── 我
        ├── 老婆
        ├── 爷爷
        └── 小宝
           └── 每个人的打卡项目（吃药 / 跳绳 / ...）
```

| 概念 | 定义 | 说明 |
|---|---|---|
| 账号 | 唯一主体 | 你本人 |
| 成员 | 账号下一个人名 + 一个头像 | **纯标签**，不是账号、不能登录、无密码。作用仅两个：① 把打卡项目分组；② 区分"这是谁的" |
| 代打卡 | 由你替任何成员勾选完成 | 系统默认行为 |

**为什么这样就够**：真实使用方式是"我给你设、我替你勾、我看你做到没"。成员不需要独立身份。

✅ **已定（必选功能）**：给成员生成**成员打卡链接**，让老人/小孩在自己的设备上打开链接、只看自己、只勾自己的项目。详见 3.11。

> ⚠️ 这条功能有个前提必须说清楚：**"别人能打开链接"意味着数据必须离开你的手机**，而第一版定的是本地存储。两者有冲突，解法见 3.11.3。

**成员字段（极简 3 项）**

| 字段 | 必填 | 说明 |
|---|---|---|
| 名字 | 是 | 自定义，如"爷爷""小宝"。默认自带"我"且不可删除 |
| 头像 | 否 | 从预置头像选；不选则按名字自动生成色块 + 首字 |
| 排序 | 自动 | 可拖拽，决定列表与打卡页顺序 |

- 成员删除：软删除，历史打卡记录保留（否则统计会断）
- 🟡 是否允许重名？（建议允许，靠头像区分）

## 3. 功能需求

### 3.1 成员管理（P0）

- 新增成员：填名字（可选头像）→ 保存，10 秒内完成
- 编辑名字/头像、拖拽排序、删除
- 头像：**一组预置头像**（不同底色 + 图标，🧓👦👩👨 或色块首字），保证 4-6 人一眼区分
- ✅ **入口位置（已定）**：两处——①「设置 → 成员管理」（完整管理：增删改、排序）；② 首页成员视图点头像（快路，直达该成员详情）。成员管理**不占底部 Tab**

### 3.2 打卡项目创建（P0）

**创建流程**：选模板（或自定义）→ 选成员 → 填项目名 → 设时间规则 → 设疗程（可选）→ 保存

**入口位置（已定）**：今日清单右上角「⋯」→ 新建打卡项。**不占底部 Tab，不放首页大按钮**——建项目是低频操作，不该挤占主界面。

#### 3.2.1 时间规则体系（已定：规则尽可能全，但按使用频率分层）

**设计原则**：功能都给，但**按常用程度分层**，不让低频规则挤占主流程。

- **高频（第一层，创建时默认展示）**：日常 90% 的场景
- **低频（第二层，"更多规则"折叠在下面）**：需要时点开
- **高级（第三层，"高级设置"再折叠一层）**：极少用，别挡路

#### 第一层：高频规则（默认可见）

| 规则 | 说明 | 例子 |
|---|---|---|
| 每日单次固定时刻 | 每天同一时间 | 跳绳，每晚 20:00 |
| 一日 N 次 · 跟随三餐 | 早/中/晚 前或后，可加偏移 | 吃药，一天三次，饭后 30 分钟 |
| 一日 N 次 · 自定义时刻 | 自由加 N 个时间点 | 吃药，15:00 和 22:00 |

#### 第二层：低频规则（折叠在"更多规则"里）

| 规则 | 说明 | 例子 |
|---|---|---|
| 每周指定几天 | 勾选周几，如周一/三/五；或"每周末" | 每周三次跑步 |
| 间隔重复 | 每 N 小时一次，可限定起止时段 | 每 2 小时喝水（9:00–21:00） |
| 每日多次 · 不等间隔 | 直接列时刻表（其实与"自定义时刻"同构，只是数量多） | 早 7:00、午 12:00、下午 15:00、晚 21:00 |

#### 第三层：高级规则（再折叠，或放到"高级设置"）

| 规则 | 说明 | 例子 |
|---|---|---|
| 单双周 / 隔周 | 每两周一次 | 隔周一次大扫除 |
| 每月固定日 | 每月 1 号、15 号 | 每月 1 号交水电费 |
| 按完成推下次（浮动间隔） | 上次完成后 N 小时再提醒，不看钟点 | 每 4 小时换一次药贴 · ❌ **P1 不做，P2 再做** |
| 多个时间段 | 上下午各一组时间 | 上午 9/11 点，下午 15/17 点 |

> 💡 这些规则**建议底层统一建一个"排程表达式"**（能表达"每天/每周几/每隔 N 天/每隔 N 小时"的组合），界面再分成三层展示。这样以后加新规则，不用动底层数据结构，只加一个界面入口。

#### 规则可以叠加（这是关键）

真实的规则往往是"两个条件的交集"，例如：

- **"仅工作日" + "每天 8:00"** → 工作日早上吃维生素
- **"每周一三五" + "每天 20:00"** → 隔天跳绳
- **"疗程 7 天" + "每天 3 次"**

因此设计上需要：**重复规则（哪天做）× 时刻规则（几点做）× 疗程（做到哪天为止）三个维度正交组合**，而不是让用户从一张大表里选一个。

🟡 建议第二层里额外给一个"**仅工作日 / 仅周末**"的快捷开关，这个在中式生活场景里极其常用。

**疗程（已定：支持）**

- 可设为"有期限"：指定开始/结束日期，或"连续 N 天"
- 到期自动**归档**，停止提醒，历史完整保留
- 归档项目可"再来一轮"（复制成新疗程）
- 无期限项目 = 长期习惯（如跳绳），可手动暂停/恢复
- 🟡 到期前轻提示"疗程即将结束，是否续上"？
- ✅ **改规则不影响历史（已定）**：修改时间规则后，已经发生的记录按当时规则计算，不会变成"迟到"。历史是历史，改规则只影响以后
- ✅ **暂停 / 归档 / 删除的语义区别（已定）**：
  - 暂停：不提醒、不出现在今日，记录保留，随时恢复
  - 归档：疗程结束或主动收起，同上但需要"再来一轮"才重新开始
  - 删除：项目消失，记录保留但不再挂在该项目下（日历里仍能看到那天做过这件事）
  - 三者都不抹历史

**项目字段一览**

| 字段 | 必填 | 说明 |
|---|---|---|
| 所属成员 | 是 | 从成员列表选 |
| 项目名 | 是 | 如"降压药""跳绳 200 个" |
| 图标/颜色 | 否 | 预置图标库，或首字色块 |
| 时间规则 | 是 | 见 3.2.1 三层规则体系 |
| 疗程 | 否 | 起止日期或连续 N 天；不填=长期 |
| 提醒开关 | 默认开 | 到点系统通知 |
| 说明 | 否 | 如"白色药片 2 粒，饭后半小时"（**事前**说明，区别于打卡时的备注） |

### 3.3 模板库（已定：纳入第一版）

**目的**：让新建项目从"选一个模板、改个时间"开始，而不是从空白表单开始。这是"简洁"最有效的抓手。

| 分类 | 模板 | 默认可用的时间规则 |

| 健康 | 喝水 | 一日 N 次自定义时刻（如 9/11/14/16/19） |
| 健康 | 量血压 | 每日单次（早 8:00） |
| 健康 | 测血糖 | 每日单次（早 7:30） |
| 健康 | 补充维生素 | 每日单次（早 8:30） |
| 运动 | 跳绳 | 每日单次（晚 20:00） |
| 运动 | 散步/遛弯 | 每日单次（晚 19:00） |
| 运动 | 拉伸 | 每日单次（晚 21:00） |
| 学习 | 作业 | 每日单次（晚 19:30） |
| 学习 | 阅读 | 每日单次（晚 20:30） |
| 生活 | 早睡 | 每日单次（晚 22:30） |
| 生活 | 洗漱 | 每日两次（早 7:00 / 晚 21:30） |

- 每个模板自带：图标、颜色、默认时间规则、一句说明
- 用模板创建时，**所有字段都可改**，模板只是预填
- 🟡 是否允许用户把自定义项目"存为模板"？（P1，第一版可先不做）
- 🟡 模板是否需要按成员类型推荐？（如选"爷爷"优先显示健康类）——需引入"成员年龄/类型"字段，与极简模型有冲突，建议不做

### 3.4 打卡凭证（已定：软性、可选）

打卡时**不强制**填任何东西，但可附加凭证。

| 凭证类型 | 说明 | 优先级 |
|---|---|---|
| 文字备注 | 一句话，如"吃了 2 粒""跳了 250 个" | P0 |
| 照片 | 拍药盒、作业、体重秤等 | P0 |
| 语音 | **不做**（原需求已排除） | ❌ |

**交互原则**

- 主路径永远是**一键勾选就完成**，凭证是"完成后再补"的轻量动作，不弹窗、不打断
- 完成后该行出现"＋备注""＋照片"小按钮，点了才展开
- 已有凭证的记录带小标记（📝 / 📷），点开可看
- 🟡 项目级可选"建议拍照"（吃药类项目才提示，不强制）
- 照片本地处理：压缩后存 App 私有目录，随打卡记录一起管理

#### 3.4.1 照片跨端策略（已定：不同步，但必须"看得见存在"）

**结论：照片只在 App 本地保存，不同步到网页端。但网页端必须明确标示"这条记录原本有照片"。**

**为什么照片不同步**

| 原因 | 说明 |
|---|---|
| 体积 | 一张手机照片 2–5MB，压缩后也有几百 KB；托管环境容量有限，几个月的药盒照片就能撑爆 |
| 用途 | 照片主要是**你自己核对用**（他到底吃没吃），不是给多端浏览的社交内容 |
| 传输成本 | 走同步节点要占带宽、占空间，性价比极低 |

**但绝不"静默省略"——这是关键的产品原则**

用户最怕的不是"看不到"，而是**"不知道有、以为没有"**。如果网页上直接不显示照片，你会误以为这条记录没照片，或者以为同步出错了。

**网页端的具体呈现规则**

| 场景 | 网页端显示 |
|---|---|
| 记录没有照片 | 正常显示，无任何标记 |
| 记录有照片、但照片未同步 | 显示一个**灰色照片图标 + 文字"📷 照片在手机 App 中（未同步）"**，可点击/悬停看到原因说明 |
| 网页端自己打的无照片记录 | 正常显示 |

**一定不能做的三件事**

- ❌ 不显示、也不提示（等于骗人）
- ❌ 显示成"加载失败的破图"（像 bug）
- ❌ 显示成可以点但点不开的按钮（让人反复尝试）

**说明文案（点开后展示，把原因写清楚，别让人猜）**

> **照片未同步到这里**
> 这条打卡记录在原设备上附有照片。为节省存储与传输，照片只保存在记录该打卡的那台手机上，不会同步到网页端。
> 想看这张照片，请在**记录这条打卡的那台手机的 App** 里打开这条记录。
> （打卡时间：10 月 23 日 08:15 · 记录设备：主人的 iPhone）

**配套要求**

- 同步的数据里保留一个 `hasPhoto: true/false` 字段和一个 `photoCount`，**只传标志位，不传文件**
- App 侧需要能区分"这条记录是我这台设备拍的"还是"别的设备拍的"（🟡 若多设备都用 App，可以只在有照片的那台显示，其他设备显示同款提示）
- 🟡 未来是否支持"按需单张下载"？（即照片存在某处、点开时才拉取。第一版不做，留好 `hasPhoto` 字段就能扩展）

### 3.5 提醒通知（已定：第一版只提醒自己）

- **所有提醒一律只推送给账号持有人（你）的手机**，成员不接收任何通知
- 到点推送系统通知，文案带成员名 + 项目名："爷爷 · 该吃降压药了"
- 点通知直接进打卡页，一键勾选，不用层层点
- 同名项目多的场景：💡 建议通知里带上头像，视觉上更好认
- ✅ **二次催办（已定）**：到点未完成，**15 分钟后自动再提醒一次**
  - 每次打卡项最多催 1 次（避免刷屏），可在设置里关闭
  - 催办文案与到点提醒区分："爷爷的降压药还没打卡（15 分钟前）"
  - 🟡 若该项在两次提醒之间完成了，则取消未发出的催办
- 🟡 免打扰时段：用户明确设的时间一律提醒，只有"催办"遵守免打扰

> **范围说明**：第一版提醒仍只推给账号持有人（你）。但成员现在有了自己的打卡链接（见 3.11），**"成员设备上也能收到提醒"变成了一个自然延伸**——🟡 需你决定是否第一版就做：链接页在浏览器里做不到可靠的后台提醒（尤其 iOS），实际做法是"打开着页面时到点弹提示"，或者引导成员装 App 并登录该成员身份。详细权衡见 3.11.4。

### 3.6 打卡、漏卡与补卡（已定：三种结果，语义必须分清）

#### 3.6.1 核心问题：只有"打勾/补卡"两个按钮是不够的

如果一条记录错过后，界面只给「补卡」一个选项，用户会被迫做一件别扭的事：
**喝水、跳绳这类事，过去了就过去了，没做就是没做，但界面逼你要么打勾（等于撒谎），要么什么都不做（记录上永远挂着一个"未完成"，看着像系统出了问题）。**

真实情况有三种，而旧设计只覆盖了两种：

| 真实情况 | 旧设计 | 问题 |
|---|---|---|
| 做了，且按时 | 打勾 | ✅ 没问题 |
| 当时没点，后来确实做了（如 8 点该吃药，9 点才想起来吃） | 补卡 | ✅ 没问题 |
| **确实没做**（如那天压根没喝那杯水） | ❌ 无处表达 | 记录永远悬着，用户被暗示"你应该去补一下"，慢慢就会顺手勾掉，数据彻底失真 |

> 💡 **关键判断：补卡 = "这事我做了，只是当时没记"。绝不是"把没做的事标成做了"。**
> 这两个语义一旦混在同一个按钮里，整个产品的数据就不可信了——而"可信"正是这个产品的全部价值。

#### 3.6.2 三种结果（已定）

| 结果 | 用户动作 | 数据含义 | 统计口径 | 视觉 |
|---|---|---|---|---|
| **完成** | 点勾 | 做了，按时 | 计入完成率 + 准时率 | 实心绿勾 + "准时" |
| **补卡** | 历史页点"补卡" | 做了，但过了时间才记录（可补 30 天内） | 计入完成率，**不计入**准时率 | 空心绿勾 + "补"角标 |
| **未完成（标记）** | 点"没做"或划掉 | 明确承认没做 | 计入"未完成"，**不计入完成率分子** | 灰色横线 + "没做" |

> ✅ **时间窗口（已定）**：历史日历**回看无限制**（本地数据随便翻）；**补卡与"没做"标记都限 30 天内**；超过 30 天的记录只展示、不可改（按钮置灰 + 小字"超出可修改期限"）。判定逻辑单点实现在 `canEdit(date)`。

**第三种（"没做"）是本次新增，也是最关键的一个。**

- 作用：把"悬而未决"变成"已经结案"。数据仍然诚实（没做就是没做），但列表上不再有个东西一直扎眼
- 视觉必须<b>明显弱化</b>：灰色、行淡、名字加删除线、右侧一个灰色小叉。**不能标红**——标红等于惩罚用户，人要的是记录，不是挨骂
- 心理意义：**允许"今天没做到"，是一个关怀类产品应有的宽容度**。一瓶水没喝，不该在 App 上留下一道红痕

#### 3.6.3 "没做"的两个层次（重要区分）

| 层次 | 含义 | 交互 | 存哪 |
|---|---|---|---|
| **单次没做** | 今天这一次没做，明天照旧 | 首页/历史页对应那一条上点"没做" | 记一条 `skipped` 记录 |
| **以后都不做了** | 这个打卡项不需要了 | 项目设置里「停用」或「归档」 | 改项目状态，不再生成待办 |

> ⚠️ 这两个不要混。用户点"没做"时，如果是连着好几天都没做，应该在点了第 3 次时<b>轻问一句</b>："这项最近都没做，要不要先停掉？"——把那件真正该做的事（停用一个已经名存实亡的项目）提出来，而不是让人每天点三次"没做"。

#### 3.6.4 完整交互规则

- ✅ **补卡只发生在"过去的日子"**：今天那条直接点勾就是打卡，不叫补卡。补卡这个动作只在你回头看昨天、前天时出现

- 首页今日清单：对任意成员的项目一键勾选（代打卡）
- 支持部分完成：一天三次勾了两次 → 显示 2/3
- ✅ **漏卡后只有两个出口（已定）**：
  1. **做了，只是忘了记** → 记为补卡
  2. **没做** → 老实记一笔，这条结案
  - **不提供第三个"先不管"按钮**：因为"什么都不点"本身就会在当天结束时自动结案，再给一个按钮等于把默认行为又说一遍，白白多一次决策
  - ✅ 自动结案时机：次日 0 点后，昨日未处理项自动转为"未完成"，不再显示为"待做"
- ✅ **补卡入口只在历史页**，首页不放（避免"忘了就顺手补"）
- ✅ 补卡范围：最近 **30 天**
- ✅ 补卡计入完成率、不计入准时率；"没做"两者都不计入分子
- ✅ 记录视觉三态必须能一眼区分（见 3.6.2 表格）
- ✅ 首页分组标题文案（已定）：超时组用「今天漏了」，完成组用「已完成」，后面用「接下来」——短、直白、不绕
- ✅ 代勾标记文案（已定）：显示为「代勾」（两个字，够了）；本人点的显示「准时」
- ✅ 今日清单顶部显示**细进度条**（一根 4px 的条 + "3/9"），不做大圆环、不做百分比大字
  - 理由：这是关怀类产品，给一个克制的进度即可；做成大数字像在催人，容易有压力
- 🟡 误点撤销：勾错/点错"没做"能取消，保留操作痕迹

#### 3.6.5 统计口径（重新定义）

对一个应完成的打卡项，结果必属其一：

```
完成率 = (准时完成 + 补卡) / 应完成
准时率 = 准时完成 / 应完成
放弃率 = 明确"没做" / 应完成      ← 新增，可选展示
未处理率 = 自动结案的未完成 / 应完成
```

> 建议主界面只展示"完成率"和"准时率"；"放弃率"只在项目详情页里给，避免首页数字太多。
> 🟡 连续天数怎么算：建议"没做"**中断**连续天数，"补卡"保留连续天数（因为他确实做了）。

### 3.7 查看与统计（P1）

**首页双视图（已定：都要，可切换）**

| 视图 | 适合 | 说明 |
|---|---|---|
| 时间轴视图 | "现在该干啥" | 按时间从早到晚排，混排各成员项目，过点未完成标红/置底 |
| 成员视图 | "谁还没做完" | 按成员分组，每人一张卡片，显示 x/y 进度 |

- 切换控件在首页顶部（分段控件 `时间轴 | 成员`），**记住上次选择**
- ✅ 默认落在**时间轴视图**（提醒驱动型产品的核心是"现在该干啥"）
- 🟡 时间轴视图里"过点未完成"的处理：建议**置底并标红**，而不是留在原位标红——否则时间轴越往下越乱

**导航结构（已定：底部 3 个 Tab）**

| Tab | 页面 | 说明 |
|---|---|---|
| 今日 | 今日清单（双视图） | 主战场，App 打开即落在这里 |
| 历史 | 历史日历 + 统计 | 统计并入历史页，**不单独开第 4 个 Tab**（避免稀释首页注意力） |
| 设置 | 成员、提醒、显示、数据管理 | — |

- 建项目入口在今日清单右上角「⋯」，**不占 Tab**（低频操作）

**历史与统计**

- ✅ **不做"连续打卡天数"**（已定）
  - 理由：连续天数是一种压力装置，断了会有挫败感，人会为了保住它去补卡，数据就脏了。它把一个诚实的记录工具变成一个人为了面子篡改的东西
  - 改为展示：完成率 + 准时率 + 没做次数，三个数够用
- 日历视图：某天各成员完成情况，颜色深浅表示完成率，有"没做"的日子用暖红底标出
- 统计：连续完成天数、月度完成率、**准时率**（与补打卡区分）
- 单项目详情页：该项目历史时间线（含备注、照片）
- 🟡 数据导出（Excel/CSV）？给医生看血压记录时有用（与 3.8 的备份导出是两件事：备份是全量恢复用，导出 CSV 是给人看的报表）

### 3.8 数据存储（已定：本地为主副本，网页端为同步节点）

> 架构已在 [architecture.zh_CN.md](./architecture.zh_CN.md) 定案：App 本地数据库是**主副本**，网页端是**同步节点**。本节关心"本地这一侧要怎么管好"。

**App 本地：数据全部存手机本地，离线完全可用。**

好处：无账号体系、无隐私合规压力、离线完全可用、同步挂了也不影响用。

**范围决策记录（历史）**：早期曾考虑"只做手机端、PC 推后"，v0.8 改为"App 为主 + 网页端为同步节点"（见 architecture.zh_CN.md），网页端仍在 P3 阶段交付。

**「同一套跨平台架构」怎么保住**

App 与网页端是两套代码，但数据与规则必须统一，具体三条：

1. **业务逻辑与界面分离**：数据模型、时间规则计算、提醒调度、统计逻辑写成独立层，不直接调用手机专属 API。将来加 Web 端时这层原样复用。
2. **数据层做成"存储适配器"抽象**：现在实现一个"本地数据库适配器"，将来加"云端适配器"时只替换这一层，界面与逻辑代码不动。这也是"云端以后再说"能真成立的前提。
3. **技术栈选能多端输出的**：Flutter / React Native 都满足，避免用只支持单端的原生方案写死。

#### 3.8.1 数据导出备份（已定：P0，本版就做，但要"藏起来"）

**功能定性**：这是**保险**，不是日常功能。低频、但必须有；一旦用上就是救命。

**入口位置（已定：不能放主页）**

| 可以做 | 不能做 |
|---|---|
| 放在「设置 → 数据管理 → 导出备份」 | ❌ 首页任何位置出现"导出"按钮 |
| 或「我的 / 更多 → 数据与备份」二级页 | ❌ 打卡页、项目列表页出现入口 |
| 设置页里给一行灰色小字说明 | ❌ 弹窗推荐、红点提醒、新手引导里提及 |

> 判断标准很简单：**这个入口应该藏到"需要时找得到、不需要时看不见"的程度**。放得越显眼越像在暗示"这产品不靠谱"。

**备份内容与形式**

- **全量备份**：成员、项目与时间规则、全部打卡记录（含备注）、疗程状态、设置项；照片 🟡 可选包含（含照片的备份文件会大很多，建议提供"含照片/不含照片"两个选项）
- 形式：单个文件（`.zip` 内含 JSON + 可选照片目录），文件名带日期，如 `家庭打卡备份_2026-10-23.zip`
- 导出位置：调起系统"存储到文件 / 分享"，用户自己决定存哪（本地、网盘、微信发给自己）

**导入**

- 🟡 导入策略：**覆盖导入**（先清空再导入）为默认，简单可靠；"合并导入"留到以后
- 导入前必须二次确认，明确告知"当前数据将被替换"

**自动化程度**

- 🟡 是否做"定期自动备份到本地某目录"？（建议做轻量的：每次导出后记录日期，超过 30 天没备份就在设置页显示一行提示，**但不打扰**）

**其他本地存储要点**

- 照片存本地会占空间：需图片压缩；🟡 是否需要"只保留最近 N 个月照片"的清理策略
- 应用更新不能丢数据（数据目录与安装目录分离，基本要求）
- 🟡 是否纳入系统云备份（iCloud / Android 自动备份）——免费且几乎零成本，建议顺手支持
- 🟡 是否需要"清空所有数据"入口（危险操作，需二次确认，同样藏在设置里）

### 3.9 多端形态（已定：原生 App 为主 + 网页端辅助）

| 端 | 定位 | 优先级 |
|---|---|---|
| 手机 App（iOS + Android） | **主客户端**：原生提醒、日常打卡、全部管理功能 | P1 |
| 浏览器 / PC / 平板网页 | **同步节点 + 简洁前端**：完整视图（你）+ 成员大字页（家人） | P3 |
| 🟡 微信小程序 | 免安装，推送受限 | 暂不考虑 |

**架构原则（已定）**

- 代码结构按"多端可扩展"设计（见 3.8 三条），但第一版只发布手机端
- 手机端内部：iOS 与 Android 用同一套代码，不做两套
- 差异只在系统适配（通知权限、后台策略、返回手势）

**技术方向预判（待定，不写代码）**

| 方案 | 说明 |
|---|---|
| Flutter | 一套代码出 iOS/Android，将来可加 Web/桌面；本地数据库支持成熟；提醒调度生态可用 |
| React Native + React Web | 生态大，将来加 Web 端衔接好；需维护两套界面层 |
| 原生双端（Swift + Kotlin） | 提醒最稳，但工作量翻倍，且放弃"同架构" |
| ~~纯 Web（PWA）~~ | ❌ **排除**：iOS 上做不到稳定准时的后台提醒 |

⚠️ **提醒功能是硬约束**：真正的到点提醒需要原生能力和后台运行权限，纯 Web/PWA 在 iOS 上做不到稳定准时。既然第一版就要求到点提醒，**建议 Flutter 或 RN，排除纯 PWA**。

### 3.10 登录（已定：账号持有人免登录，成员走链接）

- **账号持有人（你）第一版不需要账号密码**，打开即用；本地存储 + 提醒只推自己，设备本身就是"你"
- 但**成员有了独立入口**（3.11 打卡链接），这意味着系统里从第一版起就存在"两种访问身份"：

| 身份 | 怎么进来 | 看到什么 | 能做什么 |
|---|---|---|---|
| 持有人（你） | 直接打开 App | 全部成员、全部项目、全部历史 | 一切 |
| 成员（爷爷/小宝） | 打开专属链接 | **只有自己的今日项目** | 勾选自己的、写自己的备注/照片 |

- 🟡 是否需要"设置一个 4 位密码锁"防止别人拿你手机打开 App？（建议可选，P2）
- 下一版上云端时再引入手机号登录；届时需要设计**本地数据迁移到云端**的流程（🟡 提前记一笔，别到时候强行让用户重录）

### 3.11 成员打卡链接（P0，必选）

**目标**：让老人/小孩在**自己的设备**上打开一个链接，只看到自己的今日事项、点一下就完成。不需要注册、不需要下载 App、不需要密码。

#### 3.11.1 使用流程（持有人的视角）

1. 成员详情页 → 点"生成打卡链接"
2. 生成一个链接 + **二维码**（老人用二维码比输入网址现实得多）
3. 分享出去：微信发给老人、"添加到主屏幕"、打印贴在冰箱上、做成二维码贴纸贴在药盒旁边
4. 🟡 链接是否需要**访问口令**（生成时设 4 位数字，打开链接先输一次），防止链接被转发给无关的人
5. 🟡 链接有效期：永久 / N 天 / 手动作废并重新生成

#### 3.11.2 成员打开链接后看到什么

- 极简一页：**只有自己的项目**，按时间排列，大字号、大按钮（这是给老人用的，字号不能按普通 App 来）
- 每个项目一个"完成了"按钮，点了变绿+打勾
- 可选：＋备注、＋照片（凭证与 3.4 一致）
- **看不到**别的成员、看不到统计、看不到整体历史（🟡 是否需要给自己看"这个月坚持了多少天"？我建议给一点点正反馈，但要极简，如"本月完成 22/30 天"）
- 🟡 是否允许成员看自己的历史日历？
- 🟡 顶部显示"爷爷，今天 3 件事"这类问候语

#### 3.11.3 ⚠️ 关键冲突：链接需要"服务器"，第一版是"本地存储"

这是这条需求带来的**结构性影响**，必须提前决策：

> 成员在**他的**手机上打开链接，数据存在**你的**手机里 → 他那边根本读不到。**"本地存储"与"远程链接"在物理上互斥。**

| 解法 | 做法 | 代价 | 第一版可行性 |
|---|---|---|---|
| **A. 最小云同步** | 只把"成员今日项目 + 勾选状态"这一小块放进云端，其他全部仍本地 | 需一台服务器 + 一个简陋后端；隐私面收窄到"只有打卡状态上云" | ✅ 可行，工作量可控 |
| **B. 局域网直连** | 手机开热点/同一 WiFi，成员设备访问你手机的局域网地址 | **零服务器、零成本、完全离线** | ⚠️ 只在同一 Wi-Fi 下有效；出门就失效；iOS 后台限制多 |
| **C. 链接指向 App 通知** | 严格说不是链接，而是给成员装 App 用成员身份登录 | 又回到了多端 + 账号体系 | ❌ 与"极简"冲突 |
| **D. 只做二维码"手动确认"** | 生成二维码只是给你自己扫，不解决成员独立操作 | 不满足需求 | ❌ |

> 💡 **我的判断**：选 **A**，但把云端的范围压到最小——只有"今日清单 + 勾选状态"这些**不含照片、不含历史统计**的轻量数据同步，照片和历史仍留在你手机本地（照片可以只在持有人侧展示）。这样既满足"老人自己点"，又不用建一整套云端账号体系。
>
> 但这会推翻 v0.4 的"第一版完全不上云"。**需要你确认这个取舍**：要么接受"最小上云"，要么退到 B（局域网，仅限家里用），要么把链接功能推迟。

#### 3.11.4 成员设备上的提醒

- 浏览器页面**做不到可靠的后台推送**（iOS Safari 尤其差）
- 可行做法：
  - 页面**保持打开**时（如平板常驻在客厅、挂在墙上）到点弹提示 + 声音 → 这个场景其实很真实，正好对应之前的"看板"
  - 或引导成员把页面"添加到主屏幕"，部分系统能获得有限的推送能力
- 🟡 需你决定：第一版成员端提醒就做"页面打开时提醒"够不够？

#### 3.11.5 权限与数据边界

- 成员链接**只能**读自己的项目、只能写自己的打卡记录（最小权限）
- 一旦链接泄露，别人也能替你家人打卡 → 所以 🟡 口令 + 可作废重新生成，两个都建议做
- 持有人可随时**作废某个成员的所有链接**（成员换设备、链接外泄）
- 🟡 是否需要记录"这次打卡是哪台设备点的"？（有助于识别异常，但增加复杂度）

#### 3.11.6 记录归属

成员在自己设备上打的卡，与持有人代打的卡，**在记录上要能区分**（🟡 是否需要在历史里显示"由本人完成" vs "由持有人代勾"）。这对"到底是他自己点的吗"这件事有实际意义。

## 4. 典型使用场景

**场景一：给父母设吃药**
新建成员"爷爷" → 从模板选"吃药"（时间已预填一日三次饭后 30 分钟）→ 设为 7 天疗程 → 到点收到"爷爷 · 该吃降压药了" → 打电话确认他吃了 → 勾上，写"吃了 2 粒"→ 第 7 天疗程结束自动归档，下周"再来一轮"。

**场景二：小孩跳绳**
建"小宝" → 模板"跳绳"（默认晚 20:00）→ 改成每天 200 个 → 到点提醒 → 孩子跳完说一声，勾上并记"跳了 250 个" → 月底看坚持天数。

**场景三：自己周末补记**
周一想起上周五忘勾喝水 → 进日历补勾，标记为"补" → 月末发现完成率高但准时率一般，这个数据才诚实。

**场景四：换手机**
导出备份文件 → 新手机导入 → 成员、项目、历史记录全部还在。

> 注：第一版没有 PC 端，所有操作都在手机上完成。电脑上想用要等下一版。

**场景五：老人自己点（打卡链接）**
你给"爷爷"生成打卡链接 + 二维码，打印贴在药盒旁边 → 爷爷拿手机扫一下（或你把链接存到他手机主屏幕），打开就是一个大字界面："爷爷，今天 3 件事" → 吃完药点"完成了" → 你手机上立刻能看到他 1/3 完成，且标注"由本人完成"。

**场景六：客厅平板常驻**
把"爷爷"的链接在旧平板上打开，挂到客厅墙上，页面一直开着 → 到点页面自己弹提示 + 响铃 → 老人走过去点一下。这就是之前说的"看板"场景，用链接实现，不需要 PC 端。

## 5. 决策清单

### 5.1 已确认的核心决策（18 项）

| # | 决策 |
|---|---|
| 1 | 账号体系：一个账号 + 成员标签，无档案、无登录 |
| 2 | 成员可代打卡（默认行为） |
| 3 | 打卡凭证：文字备注 / 照片，均可选，不强制 |
| 4 | 打卡结果三态：完成 / 补卡 / 没做 |
| 5 | 支持疗程（起止日期 / 连续 N 天） |
| 6 | 首页时间轴 / 成员双视图可切换，默认时间轴 |
| 7 | 预置模板库（12 个） |
| 8 | 提醒只推持有人；漏卡 15 分钟后二次催办 |
| 9 | 成员打卡链接为必选功能（P3） |
| 10 | 提醒必须锁屏准时 → 原生 App 为主 |
| 11 | 网页端 = 同步节点 + 简洁前端，只做"看 + 打卡" |
| 12 | 数据以本地为主副本，网页端可断可续同步 |
| 13 | 照片不同步网页，但网页端必须标示"原件有照片" |
| 14 | 导出备份 P0，入口藏在设置里，主页不出现 |
| 15 | 时间规则尽可能全，按频率分三层 |
| 16 | 导航：底部 3 Tab；补卡只在历史页；建项目不占 Tab |
| 17 | 不做连续打卡天数 |
| 18 | 改规则不影响历史；暂停/归档/删除语义严格区分 |

### 5.2 仍按默认值执行的项（🟡 可推翻）

- 补打卡范围：最近 30 天
- 首页"过点未完成"置底并标红
- 备份提供"含照片 / 不含照片"两个选项，默认不含
- 恢复策略：覆盖式 + 二次确认
- 30 天未备份在设置页轻提示（不打扰）
- "仅工作日 / 仅周末"快捷开关
- 同步码全家人共用一把
- 网页端家人页：备注自己可见，看不到别人写的
- 技术栈：Flutter + Node/SQLite

## 6. 开发范围

**P1 — 原生 App 单机版（做完就是一个能用的产品）**

1. 免登录，打开即用，数据存本地
2. 成员：增删改 + 拖拽排序 + 预置头像
3. 模板库（12 个预置模板）
4. 建项目：三层时间规则 + 疗程 + 说明 + 启停/归档/删除
5. 原生到点通知 + 15 分钟二次催办
6. 一键打卡 + 三态（完成/补卡/没做）+ 文字/照片凭证
7. 首页双视图（时间轴 / 成员）
8. 数据导出备份（P0，入口隐藏）

**P2 — 回顾**

9. 历史日历 + 某日明细
10. 补卡（近 30 天）
11. 统计：完成率 / 准时率（不做连续天数）

**P3 — 网页端与同步**

12. 网页服务 + SQLite + 可断可续同步协议
13. 同步码配对
14. 家人大字打卡页
15. 持有人 PC/平板完整视图
16. 成员打卡链接（生成/作废/口令）

**明确不做**：连续打卡天数、社交排行榜、付费体系、小程序、照片跨端同步、成员独立注册登录。

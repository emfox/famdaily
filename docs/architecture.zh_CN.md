# Famdaily 架构说明

## 1. 决策结论

**否决"纯网页应用"路线。采用混合架构：**

| 角色 | 承担者 | 职责 |
|---|---|---|
| 主客户端 | **原生 App**（iOS/Android） | 提醒（锁屏准时响）、日常打卡、全部数据**本地优先**存储 |
| 同步节点 + 简洁前端 | **网页端**（WorkBuddy 发布的 Web 应用） | ① 同步数据的中转站；② 轻量操作入口（PC、平板看板、成员用手机比原生更好的场景） |
| 数据主副本 | **本地** | 离线可用，不依赖网络 |

**决策依据**："提醒必须锁屏准时响"——这条是硬要求，纯网页做不到，所以 App 必须是主角。但网页顺带解决了"成员链接、平板看板、跨设备"三件事，作为配角价值很高。

## 2. 为什么不选"纯网页"，但要网页（回顾）

| 维度 | 纯网页 | 混合（本方案） |
|---|---|---|
| 到点提醒 | ❌ 只能日历兜底 | ✅ 原生通知 |
| 开发速度 | ✅ 快 | ⚠️ 中（两套东西，但共用一套 JSON 格式） |
| 成员链接 / 平板看板 / PC | ✅ 天然满足 | ✅ 同样天然满足 |
| 数据可控 | ❌ 托管 | ✅ 本地为主 |

## 3. ⚠️ 已核实的技术边界（必须先知道）

**这条方案听起来完美，但有一个硬约束必须摊开说：**

WorkBuddy 的发布机制是——**在这个沙箱里跑一个服务，然后把端口映射到一个公开链接**。由此推出三条事实：

| 事实 | 后果 |
|---|---|
| 服务是**沙箱内的进程**，靠"应用自启动"维持 | 沙箱休眠/回收时，服务**可能不在跑**。网页链接会打不开，同步失败 |
| 沙箱资源是**临时计算资源**，不是长期数据库托管 | 无法承诺 7×24 在线的服务等级；数据库文件在应用目录里，**没有面向用户的备份/恢复承诺** |
| 发布行为本身绑定你这个环境和发布记录 | 换环境、重发都可能影响数据 |

**所以这个方案的定位要诚实一点：**

> ✅ 它是一个**"你和我都在场时"可用的同步服务**：开着的时候全家都能同步、成员能打卡。
> ❌ 它不是一个能承诺"永远在线"的生产服务器。

**这意味着两个必须做的设计：**

1. **本地为主不是可选项，是唯一可靠的真相来源。** App 本地数据库是主副本，网页是副本/中转。哪怕网页挂一整周，App 仍然完全可用。
2. **同步必须"可断可续、最终一致"，不能是"必须在线才能用"。**
   - 每次同步前，先比对双方的数据版本
   - 断网/服务不可用时，标记"待同步"，联网后自动补传
   - 冲突策略：🟡 **以"打卡记录"为例，同一任务同一天以"已完成"优先**（打卡是幂等的，做过就是做过，不会因为冲突丢）；成员/项目的编辑以"最后修改时间"为准

## 4. 同步方案设计

**同步什么、不同步什么**（这是控制复杂度的关键）

| 数据 | 是否同步到网页 | 理由 |
|---|---|---|
| 成员列表 | ✅ | 体积小，需要多端一致 |
| 打卡项目与时间规则 | ✅ | 同上 |
| 打卡记录（完成状态、备注文字） | ✅ | 核心数据 |
| 照片 | 🟡 **建议不同步**（只留本地） | 体积大，托管环境容量有限；而且照片只在你自己手机上看，不需要跨端 |
| 统计结果 | ❌ 不同步 | 由记录实时算出，不存冗余 |

> 💡 如果照片不同步，成员在网页上打卡就没法附照片。建议：**成员端只支持文字备注，照片只在持有人 App 内**。这个取舍应该问题不大，但需你确认。

**同步时机**

- App 启动时、前后台切换时、下拉刷新时、有本地变更后 N 秒（防抖）
- 🟡 是否做"实时推送"？（成本高，建议第一版用"打开时同步"就够）

**身份与配对（这是新的复杂度）**

网页端要认得出"这是谁家的数据"，需要一个轻量的配对机制：

1. App 首次开启同步时，生成一个**家庭同步码**（一串长随机字符，等价于"你家的钥匙"）
2. 网页首次打开时输入这个码（或扫 App 里的二维码），之后记住
3. 🟡 是否需要多人共用同一同步码（全家共用一把钥匙）——**建议是**，简单直接，符合"极简单账号"的思路

**冲突与多端并发**

- 🟡 两台设备同时改同一个项目怎么办？（建议：最后写入生效，并保留"最近修改"记录，不做复杂的合并）
- 🟡 是否需要"操作日志"？（可以看到谁在什么时候改了啥，对排查"为什么少了一条记录"很有用，建议 P1）

### 4.1 P3 第一阶段已落地（服务端 + 协议 + App 客户端）

上面那张表里标 🟡 的几项都已经拍板并实现了。**协议细节在
[sync-protocol.zh_CN.md](sync-protocol.zh_CN.md)，这里只放结论。**

| 当时的问题 | 现在的答案 | 落在哪 |
|---|---|---|
| 照片同步吗 | **不同步**。收到即丢，本地路径也不往外发 | `CheckinDto` 编解码两头都不带 `photo_path` |
| 多人共用一把钥匙吗 | **共用**。一笔 `family_id`，每台设备一个 `device_id` | `server/src/pair.mjs` |
| 冲突怎么办 | `members`/`tasks`/`settings` 按 `updated_at_ms` 取晚（相等取远端，为的是两端可复现）；`checkins` **不看时间**，看状态强弱 | `app/lib/data/sync/sync_merge.dart` |
| 操作日志 | `change_logs` 只写不读（**唯一例外是撤销**，见下） | `AppDatabase.deletedCheckinKeys` |
| 打卡怎么撤销 | **显式声明** `removedCheckins`，不靠"全量里没有它" | `server/src/sync.mjs`、`docs/sync-protocol.zh_CN.md` §4.4 |

**推的是全量当前状态，不是变更集。** 家庭规模下约 150KB，比维护变更集
简单一个数量级，也不会有"漏推某种操作"这种只在半夜发作的 bug。

**唯一的例外是打卡撤销。** 「我删了」和「我从来就没有」必须分开表达——
新设备第一次同步推 `checkins: []`（它确实一条都没有），如果按"全量里
没有就是撤销"去推断，另一台刚打的卡会被一次性全部打成墓碑，两边一起
归零，而日志里"写入 N 行、被拒 0 条"一切正常。所以撤销走一条独立的
显式声明，凭据是本地 `change_logs` 里那条 `op = 'delete'` 的记录
（`entity_id` 存三元组 `任务id|日期|序号`）。这也是 `change_logs`
第一次被读。

**服务端只做三件事**：存行、给每行发一个单调递增的 `server_at_ms`、
按 `since` 把增量吐回去。它**不解释规则 JSON**，不重算统计，不发通知。
规则内容只有客户端懂，服务端一旦开始解释，就要求两端的规则版本永远同步演进，
而这正是最容易被忽略的那种耦合。

### 4.2 这一阶段明确不做的事

写在文档里比写在脑子里有用，因为它们都是"看起来顺手就能加"的东西。

| 不做 | 为什么 | 真要做的代价 |
|---|---|---|
| 字段级合并 | 两台设备在同一分钟改同一个项目的不同字段，后改的会覆盖先改的全部。家庭规模下概率极低 | 每个字段要独立时间戳，行宽翻倍，合并规则爆炸 |
| 服务端发推送通知 | 沙箱不 7×24，推送服务是另一套基础设施 | 提醒必须留在本机，这本来也是设计前提 |
| 照片上传 | 沙箱容量没有承诺，且照片是隐私最重的数据 | 对象存储 + 生命周期管理 + 加密 |
| 实时同步（websocket） | 需要常驻连接，与"服务会休眠"直接冲突 | 改成轮询反而更稳 |
| 网页端 | 这一阶段只做 App 与协议 | 见 §5，网页端只做"看 + 打卡" |
| token 轮换的自动续期 | 轮换会让**其他设备全部失效**，必须由人来决定 | 多设备会话管理 |

**一条必须记住的边界**：一台设备离线很久、它的打卡从没到过服务端时，
另一台推全量，服务端无从判断"这条是被撤销了还是他那儿从来没有"。
结果是**留下而不是删掉**。方向是对的——宁可多一条，不能少一条。

## 5. 网页端的两副面孔

**页面能力边界（已定）**：网页端只做"看 + 打卡"，**不含**成员管理、建项目、设置项修改。因为功能少的地方不会有两种实现打架，用户不会遇到"网页上改了半天 App 没生效"。

同一个网页，针对不同访问者呈现不同界面（由链接/同步码决定）：

| 访问者 | 看到什么 | 能力 |
|---|---|---|
| **你**（持有人，PC/平板） | 完整视图：所有成员、今日清单、历史日历 | 看 + 打卡（不含管理功能） |
| **某个成员**（如爷爷的链接） | 极简大字页面，只有自己的今日项目 | 只能勾自己的、写自己的文字备注 |

> 这正是需求文档 3.11「成员打卡链接」与 3.9「平板看板」的落地方式——**网页端一套代码，两种形态**。

## 7. 技术栈（已定，详见 tech-stack.zh_CN.md）

| 部分 | 选型 | 理由 |
|---|---|---|
| 原生 App | **Flutter ≥3.44 + Drift + Riverpod** | 一套代码出双端；本地关系型数据库成熟；原生通知插件完善 |
| 网页端 | **React 或 Vue + 同一套 TypeScript 数据模型** | 与服务端配合最顺；关键是**数据模型（JSON Schema）必须与 App 完全一致** |
| 网页服务 | **Node.js (Express/Fastify) + SQLite** | 沙箱原生支持，无需额外数据库服务；轻量够用 |
| 数据格式 | **一份共享的 JSON Schema 定义** | App 与网页共用，避免两端字段理解不一致 |

> ⚠️ Flutter 写 App + Web 写网页 = 两套代码，无法避免（因为要"原生 App"）。但通过**共享数据模型 + `domain/` 层纯 Dart 规则代码作为参考实现**把重复度降到最低。

## 8. 这个架构新引入的风险（如实列出）

| 风险 | 影响 | 缓解 |
|---|---|---|
| 🔴 网页服务不稳定（沙箱休眠/回收） | 同步失败、成员打卡打不开 | 本地为主；App 完全离线可用；同步失败不打扰用户，静默重试 |
| 🔴 数据无备份承诺 | 几年记录可能丢 | **App 本地副本 + 定期导出备份**（双保险） |
| 🟠 双端数据模型不一致 | 同步出错、数据串味 | 共享 JSON Schema + 同步层写测试 |
| 🟠 两套代码维护成本 | 改一个功能要改两处 | 网页端只做"查看+打卡"，管理功能只在 App 内做 |
| 🟡 工作量比纯网页大 | 工期变长 | 分阶段：先 App 跑通，再补同步 |

> 💡 一条建议：**网页端不要追求功能对齐 App，只做"看 + 打卡"**。管理成员、建项目这些低频操作只在 App 里做，网页端能省掉一半工作量，也避免双端维护地狱。

## 9. 分阶段落地建议

| 阶段 | 交付 | 说明 |
|---|---|---|
| **P1** | 原生 App 单机版 | 成员、模板、项目、提醒、打卡、补打卡、统计 —— 完全离线可用，**这已经是一个能用的产品** |
| **P2** | 数据导出/导入 | 换机不丢数据（本地方案的底线） |
| **P3** | 网页端 + 同步 | 成员链接、PC/平板视图、跨设备同步 |
| **P4** | 打磨 | 冲突处理、操作日志、离线队列优化 |

> 这个顺序的好处：**任何时候停下，手上都是一个能用的东西**。不会出现"做到一半两边都没做完"的局面。

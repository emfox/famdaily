# 同步协议（P3 第一阶段）

> **一句话：App 本地库是唯一真相源，服务端只是中转站 + 一个总在睡觉的公共记事本。**

三条硬约束决定了下面所有的设计：

| 约束 | 后果 |
|---|---|
| 沙箱会休眠，服务不是 7×24 在线 | 同步必须可断可续，**离线是常态不是异常** |
| 沙箱数据没有备份承诺 | 丢服务端不能丢数据，**本地是兜底** |
| 不能出现"必须联网才能用" | 任何同步失败都不阻塞、不弹窗 |

---

## 1. 接口

基址：`https://<发布域名>/`，所有路径前缀无版本号（`/health`、`/pair/*`、`/sync`）。

| 方法 | 路径 | 鉴权 | 用途 |
|---|---|---|---|
| GET | `/health` | 无 | 存活探针。返回 `families` / `cursor` / `pairEnabled` |
| POST | `/pair/new` | `X-Pair-Secret` | 建家庭，返回一次性同步码（10 分钟有效） |
| GET | `/pair/:code` | 码即凭据 | 配对前预览「这是我家的谁谁谁」 |
| POST | `/pair/claim` | 同步码 | 码换长期 token，码即刻作废 |
| POST | `/pair/rotate` | Bearer | 轮换 token，**其他设备全部失效** |
| POST | `/sync` | Bearer | 推全量 + 拉增量，一个往返 |

**推拉合成一个请求**：沙箱一次往返的成本远高于一次本地 CPU，断在半路的
窗口也只有一个。分成两个请求会留下"推成功了拉失败"的半截状态。

---

## 2. 鉴权

### 2.1 同步码

格式 `FAM-XXXX-XXXX-XXXX`，字母表 31 个字符：

```
23456789ABCDEFGHJKMNPQRSTUVWXYZ
```

去掉 `0 O 1 I L`。**这不是审美选择**：同步码的唯一存在理由是
"爸爸能把它念给妈妈听、妈妈能手输进去"。只要有一个字符在纸上会被认错，
这个理由就没了，一家人就得靠截图互传——而截图会进相册，比手输更不安全。

12 个字符 ≈ 59 bit，猜不出来。

**客户端规范化输入**时：转大写、去所有非字母数字、**去掉 `FAM` 前缀**、
重新按 3-4-4 分组。`FAM` 只是展示用的装饰，不参与校验
（服务端最初把前缀算进了长度，生成的码过不了自己的校验）。

不做"智能纠错"（把 `0` 当 `O`）：那会把两个不同的码纠成同一个，
等于把可猜空间缩小一个数量级。

### 2.2 token

32 字节随机 → base64url（43 字符）。**服务端只存 `sha256`**，
库里搜不到明文。放 header 不放 URL（URL 会进日志、进历史、进 Referer）。

两种 header 都认：

```
Authorization: Bearer <token>
X-Famdaily-Token: <token>
```

### 2.3 错误码（客户端据此分类，别只看 HTTP 状态）

| HTTP | `error.code` | 客户端该做什么 |
|---|---|---|
| 401 | `unauthorized` | **停止自动重试**，设置页红字「配对已失效」 |
| 403 | `bad_pair_secret` / `bad_pair_secret` | 提示口令错 |
| 404 | `bad_code` | 提示码不对 |
| 409 | `code_used` | 提示"这个码用过了，重新生成" |
| 410 | `code_expired` | 提示"码过期了，重新生成" |
| 429 | `rate_limited` | 按 `error.retryAfterMs` 等 |
| 400 | `bad_json` / `bad_body` / `bad_since` / `too_many` | 代码 bug，记日志 |
| 503 | `pair_disabled` | 提示服务端没配对 |
| 500 | `internal` | 当网络错误处理，退避重试 |

## 3. `/sync`

### 3.1 请求

```jsonc
{
  "since": 1735689600000,        // 上次响应里的 cursor；0 = 全量拉
  "members": [ /* 全量当前状态 */ ],
  "tasks":   [ /* 全量当前状态 */ ],
  "checkins": [ /* 全量当前状态，见 §4.3 */ ],
  "settings": [ /* 白名单键 */ ]
}
```

**是全量当前状态，不是变更集。** 家庭规模下约 150KB，比维护变更集简单
一个数量级，而且没有"漏推某种操作"这种 bug。

某个字段**不传** = 这次不推这一类。传 `[]` = 我这一类一条都没有。

### 3.2 响应

```jsonc
{
  "ok": true,
  "cursor": 1792804194194,      // 本响应已覆盖到的边界 → 下次的 since
  "writeHighWater": 1792804194194, // 本批写入的最高值；没写任何东西时为 0
  "sinceReset": false,           // true = 你的 since 比服务端还新，下次从 0 全量拉
  "pulled": {
    "members":  [ /* 含墓碑：deleted_at_ms 非空 */ ],
    "tasks":    [ /* 同上 */ ],
    "checkins": [ /* 含墓碑：deleted=1 */ ],
    "settings": [ /* */ ]
  },
  "rejected": [ { "kind": "checkin", "id": "...", "reason": "FOREIGN KEY constraint failed" } ],
  "tombstoned": 1,
  "deviceId": "..."
}
```

### 3.3 两个水位，别混用

| 字段 | 含义 | 用途 |
|---|---|---|
| `cursor` | **本响应已覆盖到的边界** = `max(进来时最高值, 本批最高值)` | 唯一的拉取水位，下次传 `since` |
| `writeHighWater` | 本批真正写下去的最高 `server_at_ms`；什么都没写时 0 | 只判断"我这次推的写进去了没有" |

**为什么 `cursor` 不能是"现在的时钟"**：拉取结果必须是快照，`cursor` 只能
覆盖响应里真实包含的行。用 `Date.now()` 会把本次请求期间别人写的行也算进
覆盖范围，而那些行并没有在这份响应里 —— 它们永久丢失。

**为什么每行要一个独立的 `server_at_ms`**：整批共用一个的话，同一批的行
全落在同一个水位上，下次 `> cursor` 一条也拉不到。症状是"一次建三个成员，
另一台手机上只出现零个"。

`sinceReset: true` 的处理：说明客户端手里的水位不可信（换机、时钟回拨）。
**下次请求传 `since: 0` 全量重来**，并把本地已同步标记清掉。

### 3.4 `rejected` 的处理

`rejected` 非空**仍然算成功**，但：

1. 被拒的条目**保留 dirty**，下次重推（它们不会自动好，除非依赖被补上）。
2. 记进本次结果，设置页的"上次同步"里能看到条数和第一条原因。

单条失败不回滚整批：一个坏条目不该让全家 200 条白推一次，但**必须告诉客户端**。

## 4. 合并规则

### 4.1 合并键

| 实体 | 合并键 | 为什么 |
|---|---|---|
| members | `id`（UUID） | 非 UUID 的 id 会在多端静默覆盖。**已修** |
| tasks | `id`（UUID） | — |
| **checkins** | **`(task_id, date, slot_index)`** | 打卡 id 是各端自己生成的 UUID。按 id 合并会让两个人各点一次变成**两条记录**，日历统计都算两遍 |
| settings | `key` | 只有白名单键参与 |

`checkins` 的 `id` **不进协议**：客户端拉到没有 id 的行时自己 `newId()`。

### 4.2 members / tasks

`LWW`：`updated_at_ms` 大者胜；**相等时远端胜**。

相等时选远端不是因为它更"对"，而是因为**它可复现**：两端都能算出同一个
结果，不会出现 A 认为 B 赢、B 认为 A 赢，然后两边永远不同、每次同步都
互相覆盖一次。

| 情况 | 结果 |
|---|---|
| 两边都改 | 时间戳大的整行胜（**字段级合并不做**，见 §7） |
| 一边改 | 直接应用 |
| 改 vs 删 | 比 `max(updated_at_ms, deleted_at_ms)`：改得晚 → 复活；删得晚 → 保持删 |
| 都删 | 保持删 |

**应用远端 members/tasks 不能走 `updateMember` / `updateTask`**：它们全量
覆盖，传 null 会抹掉 `deleted_at_ms` → 已删的行被"复活"。要用专用的
`applyRemote*`，逐列显式写。

### 4.3 checkins

**不按时间戳比大小**。打卡不是"最新的话就对"，而是"做过就是做过"。
用时间戳会导致"妈妈晚半小时补录了一次，把爸爸当时真做的 `done` 覆盖成
`makeup`"，准时率就悄悄掉了。

| 已有 | 推上来 | 结果 |
|---|---|---|
| `skipped` | `done` / `makeup` | 取 `done` / `makeup` |
| `done` / `makeup` | `skipped` | 保持 `done` / `makeup` |
| `done`(T1) | `done`(T2) | 取 `done_at_ms` **早**的（早的是当时真做的，晚的是补录） |
| `done` 与 `makeup` 同刻 | — | 取 `done`（准时率不能被一次补录拉下来） |
| `note` 非空 | — | 覆盖；空字符串当"没写"，不当"清空" |

`due_at_minute_of_day` 取非空的那个：它是"改规则不影响历史"的凭据，
不该被一次没有它的推送抹掉。

### 4.4 删除传播

| 实体 | 本地 | 协议 |
|---|---|---|
| members / tasks | 软删 | 整行照传，`deleted_at_ms` 非空 |
| **checkins** | **物理删** | **本地不存墓碑**。服务端存墓碑（`deleted=1`） |

`checkins` 的删除靠"全量推送里没有它"表达。服务端判定的依据是
**被删那条最后一次写入的时刻**（`updated_at_ms`）与这次推上来的写入时刻
谁更晚：

- 写入更晚 → 撤销之后又重新打了卡 → **复活**
- 否则 → 保持删除

基准必须是"被删那条的最后写入时刻"，**不是 `deleted_at_ms`，也不是"现在"**。
用 `deleted_at_ms`：墓碑刚建立时，任何稍后打的卡都被判成"更旧"，永远复活不了。
用"现在"：B 手机离线一小时再推，它的写入永远"更旧"。

**只拉不推的请求不做墓碑判断。** `checkins: []` 有两种含义：
「我本地一条都没有」和「我这次只来拉数据」。区分标志是**这个字段在不在**，
不是它是不是空数组。搞错的话所有打卡会被打上墓碑，症状是
"刚打的卡，切出去回来就没了"。

## 5. 客户端状态

同步需要的新状态全是键值，**`settings` 表装得下，不升 `schemaVersion`**：

| 键 | 含义 |
|---|---|
| `sync.deviceId` | 配对时服务端给的设备 id |
| `sync.token` | 长期 token（明文存本机，服务端只存哈希） |
| `sync.familyId` | 家庭 id |
| `sync.baseUrl` | 服务地址 |
| `sync.since` | 拉取水位 |
| `sync.dirty` | `1` = 本地有改动待推 |
| `sync.lastSuccessAtMs` | 上次成功时刻（设置页显示"3 分钟前"） |
| `sync.lastError` | 上次失败分类 + 文案 |

`change_logs` 保持现状（只写不读）。它现在的价值只剩两件事：
`pendingSyncCount` 显示"本地有改动"、排查"改动没了"时的时间线。
等打卡量到万级或引入大字段时再补 `device_id` + purge。

## 6. 触发时机与失败处理

| 时机 | 行为 |
|---|---|
| 冷启动，**在首次重排之后** | 静默拉一次，不阻塞进主界面 |
| 回前台 | 距上次 > 30 秒才拉 |
| 本地变更后 | 置 dirty，**防抖 3 秒**推 |
| 手动 | 设置 → 「同步」 |

顺序有讲究：`sync` 必须排在 `scheduler.reschedule(appLaunch)` **之后**。
同步可能带来新项目，反过来的话首次重排用的是即将过期的数据。
**不挂**在 `ReminderScheduler` 和任何读路径上。

| 失败分类 | 处理 |
|---|---|
| `network`（连不上/超时/503 休眠） | 静默，指数退避 30s→1m→3m→10m→30m，**只在内存**（重启就重来） |
| `auth`（401/403） | **停止自动重试**，设置页红字「同步码已失效」。绝不弹窗 |
| `protocol`（400/解析失败） | 停止重试，提示版本不匹配 |
| `partial`（`rejected` 非空） | 算成功，但被拒的保留 dirty，记进 `lastRejects` |

超时：连接 5 秒、整体 15 秒（沙箱冷启动要几秒）。

UI：**首页不显示任何同步状态**。设置页那一行右侧才显示「未开启 / 3 分钟前 / 待同步」。

### 应用远端数据后的收尾（顺序不能乱）

```
1. 事务内按 members → tasks → checkins → settings 应用（先父后子，外键 RESTRICT）
2. 提交
3. 成功后才写 since / lastSuccessAtMs / 清 dirty      ← 不能提前
4. 有写入则：reschedule(dataChanged) + 递增 memberRevision
```

第 4 步的"重排"不能省：远端改了规则不重排，系统里排队的还是旧时间的通知 ——
**静默错误，最难发现**。

`memberRevision` 的递增做成**可注入回调**（由 `SyncService` 持有），
避免 `SyncService` 依赖 Widget。

## 7. 已知缺陷（要告知用户，不要假装没有）

| 缺陷 | 后果 | 兜底 |
|---|---|---|
| 水位是服务端的钟 | 换机/时钟回拨会让 `since` 倒退 | `sinceReset` + 「重新同步」全量 |
| `since` 不是"确认收到" | 客户端写库失败却推进了 `since` → 漏数据 | **必须先落库成功才推进 `since`** |
| 不做字段级合并 | 两台设备同时改同一个项目的不同字段，后改的会覆盖先改的全部字段 | 家庭规模下两个人在同一分钟编辑同一个项目的概率极低 |
| 删除可能失效 | B 手机离线很久，它的打卡从没到过服务端，A 推全量时服务端无从删除 | 结果是"不丢数据"而不是"删除生效"，这个方向是对的 |
| 照片不同步 | 收到即丢 | 架构文档 §4 已定：照片只存本机 |
| 服务端不 7×24 | 沙箱休眠时同步失败 | 本地是主副本，离线完全可用 |

---

## 8. 第一阶段明确不做

照片同步 · 实时推送 / WebSocket（沙箱会睡）· 字段级合并 · 按名字去重成员 ·
`checkins` 软删列 · `change_logs` 的 `device_id` / purge · 服务端审计日志 ·
多家庭 / 多人账号 · 网页界面 · 数据库 schema 升级。
